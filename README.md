# 쇼더스 대본 품질 판정기

쇼더스(ShortUs)가 만든 쇼츠 대본을 영상으로 만들기 전에 **통과 · 보류 · 탈락**으로 판정합니다. 기준마다 어느 장면의 어느 문장이 왜 걸렸는지 진단을 함께 내고, 목소리가 잘못 읽을 표기는 바로 읽히게 고친 **고친 대본**도 냅니다.

- 좋은 대본의 기준: [data/labels/rubric.md](data/labels/rubric.md) (기준표 2.3판)
- 작업하며 내린 결정과 쓴 시간: [DECISIONS.md](DECISIONS.md) (D1~D26)
- 넣은 글의 출처: [data/SOURCES.md](data/SOURCES.md)

## 실행

필요한 것은 python 3.11 이상과 아래 둘 중 하나입니다. 따로 설치할 패키지는 없습니다.

- 이 컴퓨터에 로그인한 Claude Code(`claude` 명령). 기본값입니다.
- `.env`에 넣은 `ANTHROPIC_API_KEY`. 이 경우 `JUDGE_BACKEND=api`로 실행합니다.

```sh
./judge.sh one data/scripts/product-01-g1.json   # 대본 하나 판정
./judge.sh dev                                   # 개발용 48개를 판정하고 채점자 합의와 견줌
./judge.sh test                                  # 시험용 50개를 판정하고 견줌
./judge.sh eval results/v5                       # 저장한 결과를 다시 견줌
python3 tools/evaluate.py results/v5 --redecide  # 저장한 표 수에 지금 판정 선을 다시 적용해 견줌(모델 호출 없음)
./judge.sh labels                                # 채점자 세 명의 합의와 일치도를 다시 계산
python3 -m unittest discover tests               # 모델을 부르지 않는 부분의 테스트
```

- 모델은 기본이 `claude-haiku-5-5`이고, `JUDGE_MODEL=claude-sonnet-5-5`로 바꿀 수 있습니다.
- 동시에 판정하는 대본 수는 `JUDGE_WORKERS`로 정합니다(기본 6).
- 대본은 `python3 tools/collect.py --only <글 id> --per-source 2`로 받습니다.
  - 쇼더스 API로 글을 등록하고 대본만 받으며, 영상은 만들지 않아 크레딧이 들지 않습니다.
  - 대본 만들기는 하루 100번까지입니다. 도구가 시작할 때 남은 횟수를 확인합니다.

출력 예(개발용 대본 하나, 약 17초, 약 $0.007):

```
product-01-g1  →  탈락  (기준 1 걸림)

기준  1 [모델] 걸림
    · 장면 4: 「600W 출력으로 4분이면 물이 끓고」 '컵라면 하나 분량' 조건이 빠져 4분이 모든 양의 물에 붙어 틀린 말이 됨.
        넣은 글: 「600W 출력으로 컵라면 하나 분량의 물을 약 4분이면 끓입니다.」
...
기준  5 [코드] 걸림
    · 장면 3: 「4.5cm까지」 잘못 읽는 표기 — 영문 단위 기호 → 「4.5센티미터까지」로
    · 장면 5: 「31,200원에」 잘못 읽는 표기 — 쉼표 든 금액 → 「3만 1200원에」로
...
기준  9 [모델] 걸림
    · 장면 2: 「부피를 많이 차지하는 전기포트는 …」 장면 1과 같은 요점을 낱말만 바꿔 반복합니다.

고친 대본(표기를 목소리가 바로 읽게 바꿈, 렌더링에 이 문장을 씀):
    장면 3: 폴드케틀은 실리콘 몸체를 접으면 높이가 4.5센티미터까지 줄어듭니다.
    장면 5: 12월 31일까지 출시 기념으로 20% 할인된 3만 1200원에 판매합니다.

진단(판정에는 넣지 않음): 기준 5, 기준 9
```

`python3 -m judge <대본> --json`으로 실행하면 같은 내용을 JSON으로 받습니다. JSON에는 장면마다 넣은 글에서 근거로 삼은 문장(`grounding`)과 고친 대본(`fixed_scenes`)도 들어 있습니다.

## 1. 좋은 대본의 기준

쇼더스 영상은 대본대로 렌더링되므로, 영상의 내용과 소리는 대본에서 정해집니다. 그래서 대본만 보고 판단할 수 있는 것을 세 묶음, 10개 기준으로 나눴습니다. 화면 제목, 배경, 음악은 대본 단계에서 알 수 없어 보지 않습니다.

| 묶음 | 기준 | 걸리면 |
|---|---|---|
| 사실 | 1 넣은 글에 없는 내용이 없고 뜻이 바뀌지 않았다 · 2 숫자·날짜·이름이 같다 | **탈락** |
| 사실 | 3 넣은 글보다 세게 말하지 않았다 · 4 꼭 있어야 할 내용이 빠지지 않았다 | 보류 |
| 듣기 | 5 목소리가 잘못 읽는 표기가 없다 | 고친 대본을 냄. 자동으로 못 고치면 보류 |
| 듣기·구성 | 6 말하듯 쓴 문장 · 8 첫 장면에 무슨 얘기인지 나오고 궁금증을 푼다 · 9 되풀이하지 않는다 | 2개 이상이면 보류 |
| 듣기·구성 | 7 너무 길지 않다 · 10 마지막 장면이 끝을 맺는다 | 진단만 |

이렇게 나눈 이유는 다음과 같습니다.

- **틀린 내용이 가장 나쁩니다.** 영상으로 나가면 본 사람이 잘못 알게 되고, 시청자는 원문을 대조하지 않습니다.
  - 쇼더스 대본에서 가장 흔한 오류는 조건이 빠져 숫자가 다른 대상에 붙는 것이었습니다(「컵라면 하나 분량의 물을 4분」 → 「4분이면 물이 끓고」). 그래서 이 경우를 기준 1에 넣어 탈락으로 봅니다(D8).
  - 다만 **애매한 것은 탈락시키지 않습니다**(D15, D21). 기한·예외·잰 조건이 빠진 것은 기준 4(보류)로 보고, 이야기 속 작은 세부가 달라진 것은 걸지 않습니다(D18).
- **틀리지는 않았지만 사람이 고쳐야 하는 것은 보류입니다.** 세게 말하기(「할 수 있어요」 → 「해야 합니다」)와 핵심 정보가 빠진 것(지원 사업의 신청 기간 등)이 여기에 듭니다.
- **목소리가 잘못 읽는 표기는 쇼츠에서 가장 직접 들리는 문제입니다.** 「250g」, 「12,500원」, 「2.5%」가 그렇습니다.
  - 쇼더스 목소리를 직접 들어 확인했습니다(D5, D6).
  - 표기는 규칙으로 고칠 수 있으므로, 판정기가 고친 대본을 내고 렌더링에는 그것을 씁니다.
  - 자동으로 못 고치는 표기가 남을 때만 보류입니다. 직접 들어 「61만 원」이 「62만 원」으로 들린 것이 그런 예입니다(D25).
- **보는 사람마다 갈리는 것은 하나만으로 막지 않습니다.** 말투, 첫 장면, 되풀이가 그렇습니다.
- **길이와 끝맺음은 진단만 냅니다.** 길이는 렌더링에서 맞출 수 있습니다. 또 사람이 만든 인기 쇼츠 12편 가운데 6편이 결론 없이 끝났습니다(D7).

기준표는 2.3판입니다. 무엇을 왜 고쳤는지는 기준표 맨 아래 표와 D7·D8·D22·D25에 있습니다.

## 2. 판정 방식

```
대본 + 넣은 글
 ├─ 코드     기준 5(표기 규칙 → 고친 대본), 기준 7(읽는 시간 = 쇼더스 예상 초 × 0.87)
 ├─ 모델     사실 묶음(기준 1·2·3·4) — 3번 따로 물어 기준마다 과반
 └─ 모델     구성 묶음(기준 6·8·9·10) — 1번
          ↓ 기준마다 걸림 / 안 걸림 + 장면·인용·넣은 글 근거·이유
 판정 선(judge/verdict.py, 코드)  →  통과 · 보류 · 탈락 + 고친 대본
```

- **모델은 기준마다 걸림 여부만 답하고, 판정은 코드가 정합니다.**
  - 판정 선을 바꿀 때 지시문을 건드리지 않아도 됩니다.
  - 저장된 결과에 새 판정 선을 모델 호출 없이 다시 적용할 수 있습니다(`--redecide`). 기준표를 2.2·2.3판으로 고칠 때 이걸로 비교했습니다.
- **규칙으로 확실히 볼 수 있는 것은 코드로 봅니다.** 표기와 길이가 그렇습니다. 같은 대본에는 늘 같은 답이 나옵니다.
- **사실 묶음은 근거를 먼저 대게 합니다.** 장면마다 넣은 글의 근거 문장을 그대로 옮긴 뒤 판단하게 합니다.
- **사실 묶음은 세 번 물어 과반으로 정합니다(D11).** 한 번만 물으면 같은 대본에서 기준 1이 흔들렸고, 기준 1은 걸리면 바로 탈락입니다.
- **기준 1(탈락)과 4(보류)를 가르는 지시문을 기준표에 맞췄습니다(D18).** 4판 지시문은 「기한이 빠지면 기준 1」로 읽혀, 기준표가 기준 4의 예로 든 「할인 기한이 빠짐」을 탈락시키고 있었습니다.
- **모델은 하이쿠로 둡니다(D9, D12).** 판정은 영상을 만들기 전에 모든 대본에 돌립니다.
  - 하이쿠는 대본 하나에 약 15원입니다.
  - 소넷은 약 120원으로, 영상 한 편 값의 22~26%입니다. 개발용 일치는 1~2개 더 많았습니다.
- **모델 답을 못 받은 기준은 「판정 못 함」으로 둡니다.** 탈락이 아니면 그 대본은 보류로 냅니다. 답을 못 받았는데 통과시키는 일은 없습니다.

본 트레이드오프는 다음과 같습니다.

| 고른 것 | 버린 것 | 까닭 |
|---|---|---|
| 기준별 걸림 + 코드 판정 선 | 모델이 0~100점을 매기기 | 점수는 어디를 고칠지 알려 주지 않고, 같은 대본에서도 흔들립니다 |
| 통과·보류·탈락 세 단계 | 통과·탈락 두 단계 | 「틀리지는 않았지만 고칠 것」을 사람이 보게 남겨 둡니다 |
| 하이쿠 + 세 번 묻기 | 소넷 한 번 | 비용이 1/9이고, 개발용 일치는 1~2개 차이입니다 |
| 표기는 고친 대본 + 못 고칠 때만 보류 | 표기를 모두 보류(2.1판) / 진단만(2.2판) | 2.1판은 표기 하나로 보류가 너무 많았고(보류 37개 가운데 12개), 2.2판은 고친 표기가 렌더링에 들어간다는 보장이 없었습니다 |
| 기준 3(세게 말하기)은 보류로 둠 | 기준 3도 진단만 | 보류는 줄지만, 기준 1을 놓친 사실 오류를 기준 3이 붙잡던 경우가 사라져 통과로 새는 탈락이 1 → 2~3개로 늘었습니다(D23) |
| 탈락 기준도 과반(5판) | 세 번 모두일 때만 탈락(4판) | 지시문에 「확실할 때만 기준 1」을 넣은 뒤로는 만장일치까지 겹치면 진짜 탈락 13개 중 9개가 보류로 내려갔습니다(D19) |

## 3. 판정기가 의도대로 동작하는지 확인한 방법

### 정답 만들기

- **채점자**: 시청자 유형이 다른 채점 에이전트 세 명(20대·40대·60대)이 기준표로 대본 98개를 따로 매겼습니다. 기준마다 다수결을 정답으로 씁니다(D3).
- **확인**: 탈락으로 합의된 대본은 모두 제가 넣은 글과 나란히 놓고 확인했습니다(D4, D14, D20, D21).
  - 받아들이지 않은 5개 기준은 까닭과 함께 [data/labels/overrides.csv](data/labels/overrides.csv)에 있습니다.
  - 원칙은 하나입니다. 건 채점자가 모두 「애매」로 적었고, 시청자가 잘못 알아 손해 볼 사실이 아닌 이야기 속 세부라면 탈락으로 보지 않습니다.
- **정답의 한계**: 채점자끼리 맞는 정도(Fleiss κ, 98개)는 기준 6이 0.59, 기준 4가 0.66으로 낮고, 나머지는 0.70~0.76입니다.
  - 정답끼리 이 정도로 갈리므로, 판정기가 정답과 100% 맞기를 기대할 수 없습니다.
  - 기준표 1판에서는 κ가 0.38~0.41인 기준이 있어 기준 정의부터 고쳤습니다(D7).
- **기준 5의 정답**: 판정기와 같은 표기 규칙에, 직접 들어 찾은 잘못 읽기를 더한 것입니다(D6). 그래서 기준 5의 일치는 따로 세지 않습니다.

### 개발용과 시험용 나누기

- **개발용 48개**: 판정기의 오답을 읽고 지시문을 고치는 데 썼습니다.
  - 처음 22개와, 4판 시험에 썼던 26개를 합친 것입니다(D17).
- **시험용 50개(글 25편)**: 5판을 만드는 동안 한 번도 판정하지 않았고, 정답을 모두 확정한 뒤에 결과를 한 번만 열었습니다(D19, D26).
  - 블로그·커뮤니티·제품 소개·뉴스 글에, 쇼츠로 많이 만드는 커뮤니티 썰·후기 글 8편(대본 16개)을 더했습니다(D20).
  - `run_all`은 개발 모드에서 시험용 대본을 판정하지 못하게 막아 두었습니다.

### 결과

판정이 맞는 수와 함께 **치명 오류**를 따로 셉니다.

- **통과로 샘**: 합의가 탈락인데 판정기가 통과시킨 것. 틀린 내용이 그대로 영상으로 나가므로 가장 나쁩니다.
- **잘못 탈락**: 합의는 통과·보류인데 판정기가 탈락시킨 것. 멀쩡한 대본을 버리게 됩니다.

**최종 판정기(5판, 하이쿠, 기준표 2.3판)**

| | 대본 | 일치 | 기준선(모두 보류) | 통과로 샘 | 잘못 탈락 |
|---|---|---|---|---|---|
| 개발용, 2번 돌림 | 48 | 29 / 28 | 18 | 1 / 1 (탈락 13개 중) | 3 / 4 (35개 중) |
| **시험용, 1번** | **50** | **24 (48%, 95% 구간 35~61%)** | **20** | **2 (탈락 13개 중)** | **6 (37개 중)** |

시험용(처음 보는 대본) 혼동표:

| 합의 \ 판정기 | 통과 | 보류 | 탈락 |
|---|---|---|---|
| 통과 17 | 8 | 6 | 3 |
| 보류 20 | 8 | 9 | 3 |
| 탈락 13 | 2 | 4 | 7 |

**읽는 법**

- **전체 판정은 기준선보다 조금 나을 뿐입니다.** 24/50은 모두 보류로 냈을 때(20/50)보다 4개 많지만, 95% 구간이 겹쳐 「낫다」고 단정할 수 없습니다.
- **치명 오류는 대체로 막습니다.** 탈락 합의 13개 중 11개는 통과시키지 않았습니다. 잘못된 탈락도 4판(19개 중 7개, 37%)보다 줄었습니다(37개 중 6개, 16%).
- **가장 크게 어긋나는 곳은 기준 4와 기준 3·6입니다.**
  - 기준 4(빠진 내용): 합의 21개 중 14개를 놓쳤습니다.
  - 기준 3·6(세게 말하기, 말투): 합의보다 11개, 16개를 더 겁니다. 판정기가 「~이며」 같은 문서체를 기준표 글자 그대로 거는 데 비해 채점 에이전트는 너그럽습니다.
  - 그래서 「합의는 보류인데 판정기는 통과」(8개)와 「합의는 통과인데 판정기는 보류」(6개)가 서로 상쇄됩니다.
- **같은 대본을 두 번 돌리면 개발용 48개 중 5개(약 10%)의 판정이 바뀝니다.**

## 4. 한계와 남은 일

- **판정기는 소리를 듣지 않습니다.**
  - 표기 규칙에 걸리지 않는 잘못 읽기는 못 잡습니다. 「61만 원」이 「62만 원」으로 들리는 것 같은 경우로, 정답 98개 중 7개 대본에 있습니다.
  - 렌더링 전에 쇼더스 목소리로 장면을 읽혀 받아쓰기와 대조하는 단계가 다음 할 일입니다.
- **고친 대본을 쇼더스에 다시 넣는 부분은 만들지 않았습니다.** 판정기는 고친 문장을 낼 뿐입니다.
- **기준 4(빠진 내용)를 처음 보는 글에서 많이 놓칩니다.** 「핵심 정보 3개를 고르게 하는」 지시가 쇼츠형 글에는 맞지 않는 것으로 보입니다.
- **정답도 모델이 만든 것입니다.** 채점자가 같은 쪽으로 틀리면 합의로 걸러지지 않습니다. 탈락 합의만 사람이 확인했고, 보류·통과 사이는 확인하지 않았습니다.
- **대본이 적습니다.** 시험용 50개도 95% 구간이 26%p 벌어지고, 같은 글에서 2개씩 받아 실제로는 글 25편어치입니다.
- **쇼츠형 글은 8편만 받았습니다.** 하루 한도에 걸려 15편 중 7편(`data/sources/`의 community-14~17, product-12~14)은 못 받았습니다(D24).
